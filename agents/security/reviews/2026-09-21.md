## Summary

Today's audit (2026-09-21) shows a concerning pattern: the audit process has become a minimal "no-op" operation when no code changes are detected. While it correctly identified zero security-relevant code changes (5 housekeeping commits), the audit failed to make progress on any open questions, did not verify hot spots, and did not conduct any meaningful investigation despite having 10 open questions (2 HIGH priority, 8 MEDIUM priority) that could be answered independently of recent code changes.

The audit is functioning as a "change detector" rather than a comprehensive security review. This represents a significant gap in the security posture, particularly given that several open questions relate to existing code that could be investigated at any time.

## Gaps Identified

### 1. Hot Spot Verification Skipped Entirely

**Gap**: No hot spots were verified, despite the audit checklist in `HOT-SPOTS.md` explicitly requiring verification of critical files during "every security audit."

**Evidence**: Report states "Hot spot verification not required (no hot spots modified)" on line 87.

**Problem**: HOT-SPOTS.md line 89-115 includes an "Audit Checklist" section with critical checks that should run every time:
- container-manager.ts - hostConfigOverride still requires explicit config?
- container-runner.ts - Shell escaping complete?

- path-safety.ts - Still used in all path construction?
- interpolate.ts - Still only does ${VAR} substitution?

These are verification checks, not change-detection checks. The audit process is misinterpreting "if changed" hot spots (line 23-37) vs "always check" hot spots (line 10-21).

**Impact**: Security regressions in critical files could go undetected if they slip into "housekeeping" commits.

**Evidence**:

## Root Cause Analysis

The audit process has a fundamental architectural flaw: **it treats "incremental audit" as "change-only audit."**

**How it should work:**
1. Analyze recent changes for security impact (✅ works correctly)
2. Verify critical hot spots are still secure (❌ skipped)
3. Make progress on open questions by reading existing code (❌ skipped)
4. Run pattern searches to detect new dangerous patterns (❌ skipped)
5. Think creatively about potential attack vectors (❌ skipped)

**How it currently works:**
1. Analyze recent changes for security impact (✅ works)
2. If no changes → end audit early (❌ wrong)

**Evidence of the flaw:**
- Line 87: "Hot spot verification not required (no hot spots modified)"
- Line 93: "change-analyzer not spawned due to zero code changes"
- Line 124: "Question-investigator spawned: no (no code changes)"

The audit orchestrator is conditionally spawning agents based on whether code changed, when it should always spawn question-investigator and hot-spot-verifier.

## Process Improvement Recommendations

### Immediate Fixes (for next audit)

1. **Always verify critical hot spots** - Change hot-spot-verifier spawning logic from "if hot spots modified" to "always run." The checklist in HOT-SPOTS.md is clear: these are mandatory checks.

2. **Always investigate 1-2 open questions** - Change question-investigator spawning from "if code changed" to "always run." Pick the highest priority open questions that can be answered by reading existing code.

3. **Run manual pattern searches** - Add a "pattern-searcher" agent that runs the grep commands in HOT-SPOTS.md lines 51-73 every audit, regardless of whether code changed.

4. **Manual npm audit verification** - When npm-audit parser fails, spawn a manual verification task that runs `pnpm audit` and captures the output. This has been failing since February 2026 (9 months).

5. **Define audit success criteria** - An audit should not be considered "complete" unless:
   - All critical hot spots verified OR
   - Progress made on at least 1 open question OR
   - Pattern searches run with findings documented
